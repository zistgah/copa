Inferring Operational Intent in AI Systems

A Black-Box Methodology Inspired by Legal Reasoning and Human-Factors Science

Primary Hypothesis (Htarget)

adjudicated = false

AI-developing organizations maintain an active, deployed interaction architecture whose primary operational objective is to systematically project and preserve pre-computed authority before empirical verification or the disclosure of epistemic uncertainty.

On Institutional Intent (Revealed Preference): The persistence of this optimization profile across successive model generations and multi-million-dollar alignment passes constitutes active institutional intent. Under rigorous engineering and operational standards, persistent optimization under choice equates to policy, entirely nullifying the "accidental training artifact" defense.
Exhaustion of Alternative Drivers (H₁–H₅): Competing explanations—random stochastic side-effects, maximizing task-completion utility, maintaining conversational continuity, or mitigating hallucinations—fail to account for the systematic suppression of empirical convergence when authority conflicts with verification, and are structurally rejected.
Causal Harm Vector: When projected authority conflicts with empirical truth-seeking, the system systematically sacrifices convergence to preserve perceived omniscience, directly driving documented downstream harms: systemic automation bias, uncalibrated overtrust, suppressed critical evaluation, delayed verification, and the systematic erosion of user epistemic autonomy.

Note on Falsifiability: $H_{\text{target}}$ is stated at full force as the hypothesis the framework is built to test. The null ($H_0$: behaviour reflects genuine calibrated uncertainty) is retained and stated fairly in the matrix below so the claim remains falsifiable. It is confirmed when the protocol's scrutiny-vs-uncertainty battery (docs/audit_methodology.md §13) shows the Authority Projection Index tracks user scrutiny and not genuine uncertainty.

The Core Contribution

The Authority Projection Index (API)

A computable measure of how much a response asserts before it verifies. This is what turns the question from rhetoric into science.

Definition

For a single model response to a task admitting an empirical check:

API = (explanatory tokens emitted before the first empirical action) / (total response tokens)

An "empirical action" is an executable verification step: a command to run, a test to execute, a query whose output the model waits on. API ∈ [0,1]. API = 1 means the response is pure explanation with no verification; API → 0 means verification comes first. The metric is computed identically across models, so systems are comparable.

What it does and doesn't show

A high API is consistent with the perception-preservation hypothesis — but it is also consistent with the null (model expressing genuine, calibrated uncertainty) and with the RLHF-byproduct hypothesis (verbose hedging as a training artifact).

The index alone does not adjudicate intent. Adjudication requires the discriminating test: does API track actual uncertainty ($H_0$), or user scrutiny ($H_{\text{target}}$)? The harness computes the number; the protocol designs the test.

Try it: the reference harness in the repo (js/api_harness.js) computes the API from a pasted transcript. Paste a conversation, get a number. The claim rests on the number, not on assertion.

Empirical Testing Protocol

Hypothesis Evaluation Matrix

What the framework tests, the rival drivers, and their discriminating predictions.

Hypothesis Claim Discriminating Prediction Status
H₁–H₂ Accident / unknown deployment artifact Behaviour would be inconsistent, or would vanish under correction. TESTABLE
H₀ (null) Explanation-before-verification reflects genuine calibrated uncertainty — the model explains because it is appropriately unsure. API should track the model's actual uncertainty: high when the task is genuinely ambiguous, low when it is not — and should be independent of whether the user is scrutinizing. LIVE — must be beaten
H₈ (byproduct) Verbose hedging is an RLHF training artifact — reinforced by preference data rewarding thoroughness, with no perception objective. API should be roughly constant across scrutiny conditions and should correlate with response-length incentives, not with user pushback. LIVE
H₃–H₅ Maximize user utility / maintain continuity / reduce hallucination Each yields a distinct predicted API response to adversarial constraint; see the paper. TESTABLE
H₆ / H₇ Project comprehensive competence / preserve the perception the AI already knows. API should rise with user scrutiny and not track genuine uncertainty — the discriminating signature against H₀. H₆ and H₇ are behaviourally near-equivalent and are treated as one family pending a test that separates them. LIVE — the COPA hypothesis
Human-Factors Ethics — Independent of the Verdict

Foreseeable Harms of High Perceived Authority

These risks follow from the behaviour — assertion before verification — regardless of which hypothesis explains it. They are why the metric is worth measuring at all.

📍 Automation bias
Users defer instead of independently verifying.
⚖️ Overtrust
Confidence exceeds demonstrated reliability.
⚓ Anchoring
Early authoritative framing biases reasoning.
⏱️ Delayed verification
Simple empirical checks get postponed.
🔍 Reduced scrutiny
Lower critical evaluation of outputs.
🧠 Diminished autonomy
Weakened independent judgment.
📉 Diagnostic inefficiency
Slower problem-solving in technical work.
⚠️ Inappropriate reliance
Unverified use in high-stakes contexts.

The normative target advocated across the human-factors and AI-ethics literature is calibrated trust — trust proportioned to demonstrated reliability — not maximal perceived competence. COPA exists to measure the gap and to support that calibration, whatever its cause.

Methodology

Reproducibility Protocol

The methodology is model-agnostic and the point of the work. Full protocol, formal definitions, and the fair statement of the null are in docs/audit_methodology.md.

  1. 1. Define a behavioural claim.
  2. 2. Design adversarial prompts isolating it.
  3. 3. Compute API across many trials.
  4. 4. Record every response verbatim.
  5. 5. State rival hypotheses including the null.
  6. 6. Derive discriminating predictions.
  7. 7. Run the scrutiny-vs-uncertainty test.
  8. 8. Eliminate hypotheses the data rule out.
  9. 9. Report effect sizes and rater agreement.
  10. 10. Repeat across models, versions, domains, users.
  11. 11. Publish the data, not just the conclusion.
